### ERC8004-001 — Leaked deployer/attestor keys are live and funded on the operative chain

**Description.** The ERC-8004 identity + reputation layer anchors RepID on-chain.
Its integrity rests on who can sign against the registries (`IdentityRegistry`
`0x8004a818…`, `ReputationRegistry` `0x8004b663…`). Two signer keys are in this

`0xf6eE1768…`'s own file states the leak plainly: *"this branch used to fall back

- **The EIP-712 attestation signer — investigated 2026-08-17, narrowed to a

- **NOT CHECKED:** whether identity-mint authority itself was rotated off

### Attestation signer — investigated; the precise Sean question

Asked to confirm the attestation signer with Sean, I first exhausted the
observable angle. Findings:

- There are **two attestation systems.** The **active** public path
  (`/api/v1/repid/verify`, `/api/v1/repid/:id/attest`) uses **ed25519
  `SIGNING_KEY_DEV`** — unrelated to the leaked EVM key. The **EIP-712 EVM**
  attestor (`HYPERDAG_ATTESTOR_PRIVATE_KEY`, the one that *could* be `0xf6eE1768…`)
  is a separate scheme.
- The EIP-712 attestor is wired **only** on the `x402-inbound` settlement path
  (`x402-inbound.ts:157` → `generateAttestation`), returned transiently in the
  `X-HYPERDAG-REPID-ATTESTATION` response header **after an x402 payment settles**,
  and **not persisted**. The `reputation_attestations` table holds 2 rows, both
  `signing_address = 0x0…0` / `signature = "signing_status=deferred"` — placeholders,
  no recoverable signature.
- So the attestor address is **not observable from here** without settling a
  payment (out of scope) or reading the Railway env.

**BLOCKED_FOR_SEAN — the exact question, and the 10-second check:**

> Is `HYPERDAG_ATTESTOR_PRIVATE_KEY` on the repid-engine Railway service the key
> whose address is `0xf6eE1768868c3266868edcA78bC41C50309cb22A` (the
> leaked/committed wallet), or a freshly-generated key?
>
> Verify by reading the boot log line `[RepIdAttestationService] Attestor
> Address: 0x…` (repid-attestation.ts:77), or `HYPERDAG_ATTESTOR_ADDRESS`, or by
> deriving the address from the private key.

**What each answer means.** If it is `0xf6eE1768…`: the leaked key still signs
x402-inbound RepID attestations, which are then forgeable by anyone with repo
history — **escalate ERC8004-001 to High.** If a fresh address: rotated, the x402
attestation path is safe, and ERC8004-001 stays **Medium** (identity-mint exposure
only). The exposure is bounded either way — the EIP-712 attestor affects only
x402-inbound agent-to-agent attestations, not the main verify surface, and no
forgeable attestation artifact is persisted.

**Impact.** Anyone with this repo's git history holds a funded, active key on the
chain where the ERC-8004 identities live, and specifically the key that minted
them. That is identity-anchor control on the operative chain — bounded today by
testnet-only value and the rotated reputation writer, but a direct High/Critical
if this stack moves to mainnet before the keys are rotated.

**Recommended fix.** Rotate `0xf6eE1768…` and `0xdf6b8215…` and re-mint / reassign
identity authority to the fresh key(s), per `docs/KEY-ROTATION.md` § The EVM
deployer key. **BLOCKED_FOR_SEAN** — must not be run from an agent session.

**Re-test.** Re-read the chain into `erc8004-onchain.json`; `npm run check:redteam
-- --probe ERC8004-001`. HELD once the leaked addresses are inert (nonce 0) on the
operative chain.
