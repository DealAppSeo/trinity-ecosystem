The finding that decides the architecture

The Gloo rule is that teams may build on existing technology but are judged on code written during the window. That single sentence settles a question that looks like engineering taste and isn't.

Harness code imported as a version-pinned dependency is unambiguously existing technology, and every line written after Sept 8 is judged work. Harness code pasted into the repo during the window is ambiguous at best — it either inflates the judged diff with work that predates the contest, or forces you to argue provenance to a judge from a git log.

F1Blocked on Sean

Three unrelated constraints demand the same artifact

Contest rules are only the first of three. Two more arrive from completely different directions and land on the identical deliverable:

  • Growth. The tooling triage measured the ranking directly — skill packs and drop-ins (openclaw 387k, superpowers 276k, mattpocock/skills 230k) outrun genuinely good frameworks (swarms 7.1k, AgentStack 2.2k) by one to two orders of magnitude. The mechanism is switching cost. An SDK asks for a rewrite; a drop-in works in ten seconds and costs nothing to abandon.
  • Secret containment. Measured repid-engine/package.json carries a prepublishOnly hook that hard-refuses npm publish, because the repo is public and holds the scoring formula. A separate public wrapper is not the nicest way to let oneanother.dev consume the harness — it is the only way that neither copies nor leaks it.

Contest rules, growth mechanics and secret containment are three independent arguments for one deliverable. That makes it the critical path — and Measured VISION_VS_VERIFIED.md records it as BLOCKED_FOR_SEAN: npm publish. Nothing downstream moves until that call is made. It is the highest-leverage unblock on the board.

F2Decide before first record

The product's central promise is falsifiable by view-source today

ONE ANOTHER's non-negotiable is that no one becomes a public fundraising story and the person receiving help is never the product.

Measured 2026-08-16 Against pg_policies: the Supabase project carries 198 policies over 196 distinct tables readable by anon or PUBLIC with qualifier literally true. The publishable key maps to the anon Postgres role and ships in the browser bundle by design. Anyone who views source reads every row and column of all 196 — not the aggregates a UI renders.

There are zero beneficiary records today. That is exactly why this is the moment to decide it, and the governing principle is already written down in your own E2E plan:

The organising principle is irreversibility, not visibility: the system has zero users today, and the decisions that get expensive after users are the ones to make now.docs/E2E-TRUST-LOOP-PLAN.md

So oneanother.dev must not write beneficiary data into that schema on its current posture — either a separate project, or a dedicated schema that is deny-by-default and proven so by a check that fails the build, before the first burden record exists. A privacy promise resting on nobody having looked is not a privacy promise, and this is the one claim the product cannot afford to have retracted.

04

One landmine sits directly on the Proof-of-Care path

MeasuredFound, not fixed

An unanchored score event fails its entire INSERT

agent_repid_history.payment_proof_hash carries a UNIQUE constraint. The apply trigger fills it from a three-step fallback — the event's transaction hash, then its idempotency reference, then a hardcoded placeholder. That placeholder already occupies the unique slot.

So any trigger-applied score event with neither a transaction hash nor an idempotency key fails the whole event, not just the history row. Two in a row is all it takes.

A Proof of Care is exactly that shape — care delivered by a person rather than a payment has no transaction behind it. Make idempotency_key a hard interface requirement on the issuer, with a check that fails the build if a writer omits it. Fixing the schema is a settlement-semantics decision owned elsewhere; the interface requirement does not wait for it.

The recurring defect across every repo here is a system reporting success it has not earned — and sprint-daemon.mjs currently trusts an agent's own handoff. LongHorizon-Harness's three-role split (Manager plans · Executor acts · Auditor independently verifies before anything becomes checkpointed state) is the structural cure: a claim and its verdict come from different agents. That is worth more to this build than any additional executive.

Your harness already contains the sharper version of the idea, and it should be preserved rather than rediscovered: the agent never gets shell — the harness runs the allowlisted command and injects the real output into the prompt. Fold COO into CTO for now. There is no operation to run yet. A role whose denials don't bite is org-chart theatre, and each added role multiplies the pairwise-conflict surface the contract must check. Add it when a recurring operation exists that a human is doing by hand — that is the signal, not the org chart.

The one field the vision document requires

Your §16 locks the language, and one of the forbidden phrases is “autonomous AI pastor.” §9 states that consequential decisions return to human stewards. Right now that is a principle. The capability contract is where it becomes mechanical: a requires_human_occupancy: boolean on the role record, set true for Care Steward and Pastor. Then “an agent cannot occupy this role” is enforced by the same fail-closed check that governs every other capability, instead of by everyone remembering.

This is the cheapest possible moment — the contract is being specified this week, and Phase 4 already asks whether a role can hold another and what happens when two conflict. A field added now costs a line; added after migration it costs a migration.

The harness package is a different object, and the distinction is load-bearing. It is not ONE ANOTHER: it is existing TrustShell infrastructure, it already has other consumers, and it names no hackathon project. Publishing it before the window makes compliance stronger:

Route by role, not by vendor

Vendor is not a property of a task, so it gives a router nothing to route on. Three roles with real selection rules — Reason (frontier tier; slow and expensive is fine), Execute (optimise tokens/sec and cost; local or fast-inference), and Verify, which carries the one constraint worth defending: the verifier must be a different model family from whoever authored. Not a preference — it is what makes the check mean anything, and run-agent.mjs already refuses to auto-commit for exactly this reason.

Turnkey and deeply-customisable are one mechanism, not two. The OpenAI-compatible surface is the socket. Turnkey = the default binding points at Gloo. Custom = BYOK swaps base URL and key per role. Same contract, different binding — precisely what PR #469's binding record is for.

The real gap

It is all inert

Almost none of this needs building. BYOK sits behind a default-OFF flag, and the index records “no production caller” against module after module — calling that the harness-wide state, not a per-module gap.

So Sept 8 readiness is wiring and switching on, not greenfield. A materially smaller job than it looks, fully testable now, on existing technology. It is also LESSONS 3 exactly: a mechanism wired at one end only is worse than an absent one, because it converts a known gap into false coverage.

The competitive set is a scoreboard, and it is open

The most useful item in the 37-repo triage wasn't a tool. It was the agent-identity topic page.

Seven independent projects are building pieces of agent identity — DID-based identity with W3C Verifiable Credentials, agent credential gateways, cryptographic identity with scoped permissions and tamper-evident audit, an open standard for persistent agent identity. The largest has 82 stars.

That cuts both ways and both halves matter. Seven independent teams reached for this problem, so the need is real and is not being invented here. And nobody has won it — no incumbent, no default, no distribution. Your competition for attention is not the identity establishment; it is seven repositories with two-digit star counts, against live ERC-8004 contracts and a scoring engine with real events behind it.

That window will not stay open. ONE ANOTHER is an unusually good vehicle for it: a trust layer nobody adopts because it is a trust layer gets adopted when it is the thing that let a church coordinate care without turning a person into a public story.
